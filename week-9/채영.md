# 9장. 패키지 개발에 도움이 되는 도구와 팁

자바스크립트 패키지 개발에 도움이 되는 유명 도구들과, 실전에서 패키지를 견고하게 만들기 위한 팁을 정리한다.

---

## 9.1 패키지 개발에 도움이 되는 도구

### 9.1.1 패키지를 업로드하는 또 다른 방법 — JSR

**JSR이란?**

npm과 비슷한 역할을 하는 **자바스크립트 레지스트리**다. 타입스크립트가 자바스크립트의 슈퍼셋으로서 정적 타입 검사 등의 추가 기능을 지원하듯이, JSR은 **npm의 슈퍼셋**을 지향하며 npm이 커버하지 못하는 부분을 보완한다.

**JSR이 등장한 배경**

과거에는 자바스크립트 런타임이 사실상 Node.js뿐이었다. 하지만 지금은 **Deno, Bun, Cloudflare Workers(Workerd)** 등 새로운 런타임이 등장하면서, Node.js 환경만을 전제로 설계된 npm 레지스트리 외에 **멀티 런타임을 지원하는 새로운 레지스트리**가 필요해졌다. JSR은 이러한 필요에 의해 만들어졌다.

**JSR이 제공하는 주요 기능**

- **타입스크립트 네이티브 지원** — 타입스크립트 소스를 그대로 배포할 수 있으며, JSR이 자동으로 타입 선언과 문서를 생성한다. 별도로 `.d.ts` 파일을 만들거나 빌드 스텝을 추가할 필요가 없다.
- **ESModule만 지원** — CommonJS를 배제하고 ESModule만 지원함으로써 모듈 시스템의 일관성을 확보한다.
- **더 쉬운 배포** — npm처럼 `npm login`, `.npmrc` 설정 등을 거치지 않아도 된다. `npx jsr publish` 한 줄로 배포가 가능하다.

**JSR 배포 시 알아둘 점**

- `mod.ts` 파일은 **Deno에서 사용하는 패키지의 기본 진입점**이다. Node.js에서 `index.js`가 디렉터리의 기본 진입점 역할을 하는 것과 같은 개념이다.
- 배포 명령어: `npx jsr publish`
- JSR 패키지는 npm 프로젝트에서도 사용할 수 있다. JSR이 npm 호환 패키지를 자동으로 생성해주기 때문이다.

**참고: Deno란?**

Node.js 창시자인 **라이언 달(Ryan Dahl)**이 만든 모던 자바스크립트/타입스크립트 런타임이다. 이름은 "Node"의 글자를 재배열(anagram)한 것이다.

Deno의 주요 특징:

- **보안 중심 설계** — 파일, 네트워크, 환경변수 접근 등에 대한 권한이 기본적으로 제한되며, 필요한 권한은 `--allow-read`, `--allow-net` 등으로 명시적으로 부여해야 한다.
- **타입스크립트 기본 지원** — 별도 설정이나 `tsc` 컴파일 없이 타입스크립트를 바로 실행할 수 있다.
- **ESModule 사용** — Node.js의 CommonJS(`require`) 대신 ESModule(`import/export`)을 기본 모듈 시스템으로 사용한다.
- **URL 기반 모듈 임포트** — npm 같은 중앙 저장소 대신 URL을 통해 직접 모듈을 불러올 수 있다. (예: `import { serve } from "https://deno.land/std/http/server.ts"`)
- **브라우저 호환 API** — `fetch`, `WebSocket` 등 가능한 한 웹 표준 API와 호환되는 API를 제공한다.

### 9.1.2 복잡한 번들 프로세스를 한 번에 수행하는 도구 — tsup

7장, 8장의 예제에서는 롤업(Rollup), Vite, 바벨(Babel), esbuild 등 다양한 도구를 조합해 번들 결과물을 만들었다. 이렇게 도구마다 설정 파일을 따로 관리하는 것은 번거롭다.

**tsup**은 이 문제를 해결하기 위해 등장한 도구로, **esbuild 기반의 제로 설정(zero-config) 번들러**다.

tsup의 주요 특징:

- 별도의 복잡한 설정 없이 타입스크립트 소스를 **CJS, ESM, IIFE** 등 다양한 포맷으로 한 번에 번들링할 수 있다.
- `.d.ts` 타입 선언 파일도 자동으로 생성한다.
- 내부적으로 esbuild를 사용하므로 **빌드 속도가 매우 빠르다**.
- 트리 셰이킹, 코드 스플리팅, 소스맵 생성 등을 지원한다.
- `tsup.config.ts` 파일 하나로 모든 번들 설정을 관리할 수 있다.

```bash
# 기본 사용 예시
npx tsup src/index.ts --format cjs,esm --dts
```

### 9.1.3 구성 파일의 표준 — cosmiconfig

**cosmiconfig란?**

프로젝트의 **구성(configuration) 파일을 자동으로 탐색하고 로드**해주는 라이브러리다. 많은 오픈소스 도구(ESLint, Prettier, Babel 등)가 내부적으로 cosmiconfig를 사용해 다양한 형식의 설정 파일을 찾는다.

예를 들어 `myapp`이라는 도구의 설정을 찾을 때, cosmiconfig는 다음 순서로 탐색한다:

1. `package.json`의 `"myapp"` 키
2. `.myapprc` (JSON 또는 YAML)
3. `.myapprc.json`, `.myapprc.yaml`, `.myapprc.yml`
4. `.myapprc.js`, `.myapprc.cjs`
5. `myapp.config.js`, `myapp.config.cjs`

이렇게 하면 사용자는 자신이 선호하는 형식으로 설정 파일을 작성할 수 있고, 도구 개발자는 cosmiconfig 하나만 사용하면 모든 형식을 지원할 수 있다.

**rc 파일의 유래**

`rc`는 유닉스 계열 시스템에서 유래한 약어로, **"Run Commands"**의 줄임말이다. 유닉스 초기의 **RUNCOM**이라는 프로그램에서 비롯되었으며, 파일에 저장된 여러 명령어를 순차적으로 실행하는 기능이 있었다. 시간이 지나면서 `rc`라는 접미사가 설정 파일 이름에 붙는 전통이 되었다. (`.bashrc`, `.eslintrc`, `.prettierrc` 등)

**cosmiconfig 사용법**

찾고자 하는 구성 파일의 이름(모듈명)을 선언한 다음 `search()`를 실행하면, cosmiconfig의 규칙에 따라 현재 디렉터리부터 상위로 올라가며 구성 파일을 검색한다.

```javascript
import { cosmiconfig } from 'cosmiconfig';

const explorer = cosmiconfig('myapp');
const result = await explorer.search();
// result = { config: { ... }, filepath: '/path/to/.myapprc', isEmpty: false }
```

특정 경로의 파일을 직접 로드할 수도 있다:

```javascript
const result = await explorer.load('/path/to/myapp.config.js');
```

### 9.1.4 성능 분석을 위한 도구 — Tinybench

**Tinybench**는 자바스크립트 함수의 **성능을 벤치마크**하기 위한 경량 라이브러리다. 두 개 이상의 함수를 등록하고 실행 시간, ops/sec(초당 연산 수) 등을 비교할 수 있다.

**성능 측정 예시: lodash.isEmpty vs 커스텀 isEmpty**

`lodash.isEmpty`보다 빠르게 동작할 것으로 기대하는 커스텀 함수:

```typescript
function isLength(value) {
  return (
    typeof value === 'number' &&
    value > -1 &&
    value % 1 === 0 &&
    value <= Number.MAX_SAFE_INTEGER
  );
}

function isArrayLike(value) {
  return value != null && typeof value !== 'function' && isLength(value.length);
}

export default function isEmpty(value) {
  if (value == null) {     // == 을 사용해 null과 undefined 모두 처리
    return true;
  }

  if (isArrayLike(value)) {
    return !value.length;
  }

  const type = Object.prototype.toString.call(value);

  if (type === '[object Map]' || type === '[object Set]') {
    return !value.size;
  }

  if (type === '[object Object]') {
    for (const key in value) {
      if (Object.prototype.hasOwnProperty.call(value, key)) {
        return false;
      }
    }
    return true;
  }

  return false;
}
```

**이 함수의 동작 로직 정리:**

1. `value == null` — `==`(느슨한 비교)을 사용해 `null`과 `undefined`를 한 번에 처리한다. (원본 노트에서 `=== null`이라고 적혀 있었지만, 코드상으로는 `== null`을 의도한 것으로 보인다.)
2. **유사 배열(ArrayLike) 확인** — `length` 속성이 있는 유사 배열인지 확인한 후, `length`가 0이면 비어있다고 판단한다. 배열, 문자열, `arguments` 객체 등이 여기에 해당한다.
3. **Object.prototype.toString으로 타입 확인** — `toString.call(value)`를 사용하면 `[object Map]`, `[object Set]` 등 정확한 내부 타입을 알 수 있다. `typeof`보다 더 세밀한 타입 구분이 가능하다.
4. **Map/Set** — `size` 프로퍼티로 빠르게 비어있는지 확인한다.
5. **일반 Object** — `for...in` 루프로 열거 가능한 속성을 순회하되, `hasOwnProperty`로 프로토타입 체인의 속성을 제외하고 자기 자신의 속성만 확인한다. 하나라도 있으면 `false`를 반환한다.

**lodash.isEmpty보다 빠를 수 있는 이유:** lodash는 다양한 엣지 케이스(Buffer, TypedArray, prototype 등)를 모두 처리하느라 내부 로직이 복잡하다. 위 커스텀 함수는 가장 흔한 케이스만 빠르게 처리하므로 일반적인 사용 시나리오에서는 더 빠를 수 있다.

**Vitest를 이용한 벤치마크 실행**

Vitest는 테스트 프레임워크이지만 `bench` 기능도 내장하고 있어, 별도의 벤치마크 도구 없이도 성능 측정이 가능하다.

```typescript
import { bench, describe } from 'vitest';
import lodashIsEmpty from 'lodash.isempty';
import isEmpty from './isEmpty';

describe('isEmpty 벤치마크', () => {
  bench('커스텀 isEmpty', () => {
    isEmpty({});
    isEmpty([]);
    isEmpty('');
    isEmpty(new Map());
  });

  bench('lodash.isEmpty', () => {
    lodashIsEmpty({});
    lodashIsEmpty([]);
    lodashIsEmpty('');
    lodashIsEmpty(new Map());
  });
});
```

### 9.1.5 코드 마이그레이션을 도와주는 jscodeshift

**jscodeshift**는 Facebook(Meta)이 만든 **코드 변환(codemod) 도구**다. AST(추상 구문 트리)를 기반으로 코드를 분석하고 자동으로 변환한다.

- 대규모 코드베이스에서 API 변경, 임포트 경로 변경, 문법 업그레이드 등을 자동화할 때 유용하다.
- 단순한 텍스트 치환(find & replace)과 달리, 코드의 구조(AST)를 이해하고 변환하므로 정확하고 안전하다.
- 예를 들어 "모든 `require()` 구문을 `import`로 바꾸기", "특정 함수 호출의 인자 순서 변경" 같은 작업을 자동으로 수행할 수 있다.

## 9.2 패키지 개발에 도움 되는 팁

### 선택 아닌 필수, ESModule

이미 표준으로 자리 잡은 **ESModule을 기반으로 패키지를 작성**하는 것이 효율적이다. 꼭 필요한 경우가 아니라면 CJS/ESM 이중 패키지를 구성하거나, 불필요한 폴리필을 추가하는 것을 지양한다. 브라우저 및 Node.js 등 **타깃 환경 내에서 최대한 호환성을 높일 수 있는 구성**을 고려한다.

### package.json 최적화

- **`exports` 필드**로 모듈 진입점을 명확히 정의한다. 이를 통해 패키지 내부 파일에 대한 접근을 제어하고, CJS/ESM 분기도 깔끔하게 처리할 수 있다.
- **`engines` 필드**로 필요한 Node.js 버전을 명시한다.
- **`packageManager` 필드**로 사용하는 패키지 매니저(npm, yarn, pnpm)와 버전을 통일한다. 이를 통해 팀 내 개발 환경의 혼선을 줄일 수 있다.

### 의존성 선정과 관리

- 직접 구현해도 되는 간단한 기능을 위해 외부 라이브러리를 추가하지 않는다. (예: `is-odd` 같은 단순 유틸리티)
- 꼭 필요한 라이브러리만 사용하되, **보안 취약점**과 **모듈 호환성**(CJS/ESM)을 충분히 검토한다.
- 하위 의존성(transitive dependency)까지 관리해 **번들 크기를 최소화**한다.

### 테스트와 벤치마크

- **단위 테스트**와 **통합 테스트**를 통해 기능의 정확성을 확인한다.
- **벤치마크**를 통해 성능을 증명함으로써 사용자와 기여자에게 신뢰를 준다.
- 특히 핵심 기능은 빠짐없이 테스트해, 개발 과정에서 생길 수 있는 문제를 조기에 발견하고 수정한다.

### 문서화

- **README** — 패키지 소개, 설치 방법, 사용 예시
- **CONTRIBUTING** — 기여 방법, 개발 환경 셋업, PR 규칙
- **CHANGELOG** — 버전별 변경 사항 기록

이 세 문서를 충실히 작성하면 프로젝트가 체계적이고 협업하기 좋은 구조가 되며, 오픈소스 생태계에서 장기적인 가치를 높이는 중요한 요인이 된다.

### 지속 가능성

위 과정을 충실히 밟은 패키지는 단순한 코드 조각에 머무르지 않고, 시간이 지나도 오픈소스 생태계 내에서 가치 있게 쓰이며, 한층 더 견고하고 유용한 라이브러리로 자리매김하게 된다.
